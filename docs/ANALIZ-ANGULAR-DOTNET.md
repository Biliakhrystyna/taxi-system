# Аналіз проєкту taxi-prototype: перехід на Angular + .NET, API та доопрацювання логіки

> Зведений звіт за результатами обговорення (відновлено з попередньої сесії).
>
> **Історична нотатка:** фінальне ТЗ (розділ 7 нижче) розглядало варіант з Angular та
> OpenRouteService. Чинне технічне завдання практики використовує **Vue.js** замість
> Angular і не включає OpenRouteService — актуальна архітектура описана в
> [`ARCHITECTURE.md`](./ARCHITECTURE.md). Цей файл лишається як довідковий матеріал
> щодо обґрунтування вибору BCrypt, Open-Meteo та BackgroundService/SignalR — ці
> висновки лишаються чинними.

---

## 1. Поточний стан проєкту

Стек зараз: **Vue 3 + Pinia + Firebase Firestore + Leaflet**, ~800 рядків коду:
`App.vue`, `TaxiMap.vue`, `orderStore.js`, `firebase.js`.

- Одна SPA-сторінка без роутера, стани перемикаються через `v-if` (вибір ролі → форма входу → верифікація водія → головний екран).
- Pinia-стор — по суті весь "бекенд": auth (паролі у відкритому вигляді в Firestore ⚠️), розрахунок тарифу, статуси замовлення.
- Firestore `onSnapshot` — реалтайм-оновлення статусу замовлення й лічильників поїздок.
- Leaflet-карта з фейковою "AI"-логікою: випадкові зони дефіциту, пряма лінія замість реального маршруту.
- **.NET і реляційної БД зараз немає взагалі** — це чистий frontend-прототип на Firebase.

## 2. Наскільки складно перенести на Angular

**Не складно, помірний обсяг роботи.** Проєкт маленький, логіка проста:

| Vue | Angular-еквівалент | Складність |
|---|---|---|
| `v-if`-стани в одному компоненті | Angular Router + guards (окремі компоненти на роут) | Легко, навіть покращення |
| Pinia store (`orderStore.js`) | Angular service + RxJS `BehaviorSubject`/сигнали | Пряме перенесення 1:1 |
| `onMounted`/`watch` у `TaxiMap.vue` | `ngOnInit`/`ngOnChanges` + `effect()` | Leaflet не залежить від фреймворку, обгортка тривіальна |
| Firestore `onSnapshot` | AngularFire або SignalR/RxJS polling | Тут основна робота |
| Inline-стилі та CSS | Переносяться майже без змін | Легко |

Реалістично: одна людина, кілька вечорів на голий Angular-каркас з тим самим функціоналом (без бекенду) — це рутина, не складна задача.

## 3. Чи потрібно вводити .NET

**Так, і саме це варто зробити.** Причини:

1. Керівник спеціалізується на Angular + .NET API + БД — практика має демонструвати саме цей стек, а не "Angular + Firebase" (Firebase — це NoSQL BaaS від Google, не .NET і не SQL-база).
2. Поточний прототип має критичні навчальні "дірки", які реальний бекенд природно закриває: паролі зберігаються як plain text, немає валідації на сервері, будь-хто з ключем Firebase може писати в базу напряму.
3. Це дає змогу показати конкретні компетенції: REST API, EF Core + реляційна БД (замовлення/водії/поїздки — дуже "реляційна" за природою модель), автентифікацію (JWT), і **SignalR замість Firestore `onSnapshot`** — прямий показовий аналог "realtime" на .NET.

### Рекомендована архітектура

```
Angular (frontend)  →  ASP.NET Core Web API  →  EF Core  →  SQL Server / PostgreSQL
                              ↓
                         SignalR Hub (статус замовлення в реальному часі)
```

Таблиці: `Users` (passenger/driver, роль, хеш пароля через BCrypt/Identity), `Drivers` (клас авто, ліцензія, статус верифікації), `Orders`, `Trips` (історія), опційно `Payments`.

## 4. Як ускладнити проєкт (щоб це була повноцінна практика, а не переклад одного файлу)

**Бекенд / БД**
- ASP.NET Core Web API зі Swagger, шарова архітектура (Controllers → Services → Repositories)
- EF Core Code-First міграції, нормалізована схема зі зв'язками (1-до-багатьох Users↔Orders тощо)
- JWT-автентифікація + ролі (passenger/driver/admin) через `[Authorize(Roles=...)]`
- SignalR-хаб для статусу замовлення й позиції водія в реальному часі
- Логування (Serilog), глобальний middleware обробки помилок

**Функціонал (заміна "фейкового AI")**
- Третя роль — **адмін-панель**: підтвердження водіїв, бан користувачів, статистика поїздок
- Реальний розрахунок маршруту/відстані через OSRM або OpenRouteService замість прямої лінії
- Рейтинги/відгуки пасажир↔водій після завершення поїздки
- Історія платежів як окрема сутність, а не поле в замовленні

**Frontend (Angular)**
- Angular Router + route guards за ролями замість `v-if`-стану
- Reactive Forms з валідацією замість `required` в HTML
- HTTP interceptor для підстановки JWT-токена
- NgRx або сигнали для стану (аналог Pinia)

**Якість/DevOps** (якщо потрібно показати ширше)
- Юніт-тести: xUnit на бекенді, Jasmine/Karma на фронті
- Docker-compose (API + БД + Angular) — демонструє "розгортання"
- Мінімальний CI (GitHub Actions: build + test)

### Висновок по цьому блоку
Перенесення Vue→Angular само по собі — легка задача. Головна цінність практики буде не в переписуванні шаблонів, а в **заміні Firebase на власний .NET API з реляційною БД та SignalR** — це відповідає профілю керівника і дає реальний матеріал для звіту (схема БД, API-документація, діаграма архітектури). Починати краще з бекенду (EF Core модель + перші 3-4 ендпоінти auth/orders), а Angular-фронт підключати вже до нього, а не спочатку клонувати Vue-версію 1:1.

## 5. Де в заявлених "інноваційних функціях" бракує логіки

Три заявлені функції — **формулювання випереджають реалізацію**: по кожній є частина, яка справді закодована, і частина, якої в коді немає взагалі.

### 5.1. «Ефективний територіальний розподіл»
- **Є в коді:** `generateRandomOutskirtsZones()` в `TaxiMap.vue` — генерує 3 випадкові кола навколо центру Львова один раз при завантаженні карти, показує їх водію як теплову карту.
- **Прогалина:** зони **випадкові й статичні**, не рахують реальну кількість вільних водіїв чи попит. Немає механізму, який щось "ліквідує" чи "запобігає скупченню" — просто візуалізація фейкових плям на карті плюс цінова надбавка, якщо клієнт клікнув всередину кола.
- **Фікс (середня складність):**
  1. зберігати позиції водіїв (хоч симульовані);
  2. рахувати на бекенді співвідношення "вільні водії / активні замовлення" по зонах;
  3. SignalR/періодичний перерахунок замість `Math.random()`.
  Реалістично — `BackgroundService` в .NET, що раз на N секунд перераховує зони і штовхає оновлення через SignalR. Це вже нормальна "AI-подібна" евристика (не ML, але й не рандом).

### 5.2. «Гнучка система мотивації»
- **Є в коді:** надбавка +50 грн водію за замовлення в зоні "outskirts" — реально працює. `totalTripsCounter` реально інкрементується й відображається.
- **Прогалина:** лічильник поїздок ніде не впливає на ціну чи привілеї пасажира — просто цифра на екрані. "Утримання пасажирів" не відбувається, бо counter ні на що не розблоковує.
- **Фікс (легка складність):** правило типу "кожна 5-та поїздка — знижка 10%" або "після 10 поїздок — статус VIP з пріоритетним підбором водія" в `createOrder()`/сервісі розрахунку ціни. Пів дня роботи.

### 5.3. «Підвищена безпека перевезень»
Тут найбільший розрив — реалізована по-справжньому лише одна з чотирьох заявлених речей.

| Заявлено | Реалізовано? | Деталі |
|---|---|---|
| Предиктивний аналіз погоди | ❌ Ні | `isBadWeather` — ручний чекбокс, який вмикає сам користувач. Ніякого прогнозу чи "AI-аналізу". |
| Безпечний адаптивний маршрут | ⚠️ Частково | Намальована крива лінія (синусоїда) поверх прямої А→B. Реального обходу доріг немає. |
| Push-сповіщення | ❌ Ні | Лише модалка-попередження (`showAIWarning`) і банер (`triggerSuccess`), що зникає через 3.5 сек. Не push — елемент у тому ж вікні браузера. |
| Прямий чат з адміністрацією | ❌ Ні | Ролі "адмін" у коді немає взагалі (лише `passenger`/`driver`). Чату немає — ні UI, ні моделі повідомлень, ні хабу. |

**Складність фіксу по кожному:**
- Погода → реальний прогноз: середня. Підключити безкоштовне API (Open-Meteo) за координатами міста, мапити умови на `weather_hazard_level` автоматично замість чекбокса.
- Реальна маршрутизація: середня-висока. Підключити OSRM/OpenRouteService для реального обходу небезпечних ділянок — симуляцію "небезпечних ділянок" можна лишити власними даними, а маршрут прокладати по справжніх дорогах.
- Push-сповіщення: найлегший шлях (~1 день) — реалтайм-сповіщення в застосунку через SignalR, чесно назване "сповіщення в реальному часі", а не "push". Справжній push (Web Push API, service worker, VAPID-ключі, PWA) — окрема, суттєво складніша фіча.
- Чат з адміном: середня-висока. Нова роль `admin` з нуля, модель `Messages` (SenderId, ChatId, текст, час), SignalR hub для реалтайм-обміну, UI чату з обох боків. Найбільш трудомістка фіча зі списку.

### Чи достатньо цього для практики
Обсяг **достатній, навіть добрий** — не треба вигадувати нові функції. Ризик: якщо в звіті/на захисті прозвучать формулювання на кшталт "предиктивний ШІ-аналіз", "push-сповіщення", а викладач відкриє код і побачить чекбокс і банер — це підриває довіру до решти роботи. Два варіанти:

1. **Пом'якшити формулювання** під поточну реалізацію ("симуляція погодних умов", "сповіщення в реальному часі", "евристичний розподіл зон") — швидко, кодити нічого не треба.
2. **Дотягнути найслабші місця** (рекомендовано) — природно лягає на вже заплановану роботу з .NET: адмін-роль + чат через SignalR і реалтайм-сповіщення — та сама технологія, яку в будь-якому разі плануєте додавати для статусів замовлення.

**Пріоритет реальних доробок:** чат з адміном (нова роль + повноцінний SignalR-функціонал) і реальний розрахунок зон дефіциту на бекенді (найбільш "AI-виглядаюча" фіча, зараз повністю фейкова). Погоду й push можна лишити спрощеними з чесним формулюванням — не критично для оцінки.

## 6. Безкоштовні API замість генерації/рандому

### Погода (реальна, не чекбокс)
**Open-Meteo** — без ключа, без реєстрації, 10 000 запитів/день безкоштовно для некомерційного використання ([open-meteo.com/en/pricing](https://open-meteo.com/en/pricing)). Дає current + погодинний прогноз (опади, weathercode). Найлегший шлях — простий GET-запит з координатами міста.

Бонус: якщо брати **прогноз (forecast), а не тільки поточні дані** — це повертає слово "предиктивний" у функцію по-справжньому (закриває розрив із п. 5.3).

### Реальний безпечний маршрут (замість намальованої синусоїди)
**OpenRouteService** — безкоштовний ключ, 2000 запитів/день на директіони ([openrouteservice.org/restrictions](https://openrouteservice.org/restrictions/)). Головне: параметр **`avoid_polygons`** — передаєте координати "небезпечної зони" як полігон, сервіс сам прокладає маршрут реальними дорогами в обхід неї. Чесний спосіб реалізувати "AI-безпечний маршрут" — не імітація, а справжня альтернативна маршрутизація. (Обмеження: полігон до 200 км² і 20 км в ширину/висоту — для Львова більш ніж достатньо.)

Якщо потрібна лише пряма маршрутизація без обходу (базовий А→Б по дорогах) — можна взяти безкоштовний публічний **OSRM** (`router.project-osrm.org`) взагалі без ключа, але це демо-сервер без SLA — для головної фічі краще ORS.

### Зони дефіциту (bonus zones) — тут готового API немає
Безкоштовного API "де зараз дефіцит таксі" не існує в природі — таких даних ніхто не публікує. Цю логіку треба рахувати самим із власних даних (і це краще для захисту — це ваш алгоритм, а не чужий API):

1. Водій у статусі "онлайн" періодично шле свою позицію на бекенд (навіть раз на 10-15 сек).
2. Бекенд рахує кількість вільних водіїв на зону (сітка або кола) за останні N хвилин.
3. Рахує кількість замовлень/запитів у тій же зоні за той же період.
4. Якщо попит/пропозиція > порогу — зона позначається дефіцитною, і зникає, коли водії туди приїжджають.

Реалізується як `BackgroundService` в .NET, що перераховує раз на хвилину і штовхає оновлення через SignalR. Це нескладна евристика (не ML), але реальна, а не `Math.random()`.

### Хешування паролів: BCrypt, а не SHA-256
Найлегший варіант — вбудований `PasswordHasher` з **ASP.NET Core Identity** (якщо підключаєте Identity для JWT/ролей) або **BCrypt.Net-Next** (один NuGet-пакет, один рядок коду). SHA-256 насправді *складніше* зробити правильно, бо його треба вручну солити (генерувати сіль, зберігати окремо, конкатенувати) — це більше коду, ніж просто викликати `BCrypt.HashPassword()`. За критерієм "що легше" — беремо BCrypt/Identity, а не SHA-256.

### Як демонструвати дощ, коли надворі сонце
Два підходи, які варто поєднати:

1. **Forecast lookahead (чесний і корисний спосіб).** Замість перевірки "чи зараз дощ" — перевіряти погодинний прогноз на найближчі 24-48 год і брати найближчу годину з опадами. На захисті: "система дивиться в прогноз і превентивно попереджає про негоду навіть якщо зараз сухо" — це і є справжній "предиктивний аналіз".
2. **Явний demo-режим (стандартна інженерна практика, не обман).** Окремий, чітко підписаний перемикач "🔧 Режим симуляції для демонстрації" — окремо від реальних даних з Open-Meteo. Продакшн-логіка читає справжню погоду, demo-тумблер — свідомо позначений debug/testing інструмент (аналог feature flag). Чесна відповідь на захисті: "у production дані реальні з Open-Meteo, для контрольованої демонстрації є окремий режим імітації, позначений як такий в UI".

Третій, менш очевидний варіант про запас: на час демонстрації запросити прогноз для координат міста, де зараз реально йде дощ, і тимчасово підставити ці координати в запит — без окремого "demo-перемикача" в UI. Складніше пояснити комісії, ніж відкрито підписаний debug-режим, тому основним рекомендовано варіант 2.

**Sources:** [Open-Meteo pricing](https://open-meteo.com/en/pricing), [OpenRouteService restrictions](https://openrouteservice.org/restrictions/)

## 7. Фінальний варіант технічного завдання

*Ознайомитись та проаналізувати архітектурні вимоги до розробки асинхронних клієнт-серверних систем на основі технологій Angular та ASP.NET Core Web API. Реалізувати модуль препроцесингу та фільтрації геопросторових даних інтерактивної карти (координати точок маршруту, полігони зон попиту) за допомогою HTML5/CSS3/TypeScript на базі бібліотеки Leaflet.js. Для інтелектуальної фонової обробки даних використати фоновий сервіс (BackgroundService) ASP.NET Core із SignalR-хабом для передачі даних у реальному часі, REST API сервісу Open-Meteo для предиктивного аналізу погодних умов та REST API сервісу OpenRouteService для побудови безпечних адаптивних маршрутів в обхід небезпечних ділянок (параметр avoid_polygons). Дослідити особливості використання локального кешування даних на клієнті (localStorage) та криптографічного хешування паролів за алгоритмом BCrypt як засобів забезпечення безпеки та оптимізації передачі даних. Розробка програмного забезпечення здійснюватиметься згідно з методологією Kanban. Система контролю версій використовуватиме GIT (GitHub як віддалений репозиторій).*

**Що враховано з обговореного:**
- **Angular** замість Vue — перше речення.
- **Open-Meteo** — реальна погода + прогноз (закриває і "предиктивність", і фейковий чекбокс).
- **OpenRouteService `avoid_polygons`** — реальний безпечний маршрут в обхід зони, а не намальована крива.
- **BCrypt** — обрано як легший і коректніший за SHA-256 з ручним солінням.
- Зони дефіциту свідомо **не** прив'язані до зовнішнього API (бо такого не існує) — сформульовано як власна логіка через BackgroundService + SignalR, що відповідає дійсності.

> Якщо на захисті питатимуть "чому не chrome.storage.local" — цей пункт був специфічний саме для розширень браузера (з початкового шаблону ТЗ); `localStorage` (можливо пізніше IndexedDB) виконує ту саму роль кешування на клієнті для звичайного SPA.
